# HEIMDALL — Project Rules

## Overview

Heimdall is a cross-platform (Windows, Linux, macOS) desktop companion for Claude Code. It reads Claude Code's own data under `~/.claude/` and `~/.claude.json`, renders sessions and configuration, and (later) edits Claude Code configuration files. It is a port of Poirot, a macOS SwiftUI app. It has no backend server and no account system.

Start with `docs/port-plan.md`. Work comes from `docs/tasks/`; each task file is self-contained.

## Stack

- **Shell:** Tauri 2 with a Rust backend.
- **Rust:** a Cargo workspace. `crates/heimdall-core` holds all parsing and domain logic; `src-tauri` is the thin app shell.
- **UI:** Vue 3 + TypeScript + Tailwind CSS v4, built with Vite. Pinia for state, Vue Router for navigation.
- **Libraries:** vue-echarts (charts), markdown-it + DOMPurify (Markdown), Shiki (highlighting), Lucide (icons), TanStack Virtual (long lists).
- **Tests:** Rust unit and integration tests; Vitest + Vue Test Utils; Playwright.
- **IPC types:** generated by tauri-specta into `src/ipc/bindings.ts`.

## Layer rules

- **`heimdall-core` has no `tauri` dependency.** CI fails if `cargo tree -p heimdall-core` mentions tauri. Core functions take the Claude home and every other root as parameters, so tests run on fixture trees.
- **Platform decisions are pure data.** Core functions take a `TargetOs` argument instead of `#[cfg]`; `src-tauri/src/platform/` executes the result per OS. No trait with a single implementation.
- **All parsing happens in Rust.** The webview receives ready-to-render data. Vue does no path joins, no parsing of Claude Code files, and has no file-system or shell permissions.
- **IPC types come only from `src/ipc/bindings.ts`,** used through `src/ipc/client.ts`. Never hand-write a command name or payload type. ESLint forbids importing `@tauri-apps/api/core` outside `src/ipc/`.
- **Commands take ids, never paths** from the webview. Rust resolves ids under known roots.
- **Disk work never blocks the event loop:** commands are `async` or use `spawn_blocking`.
- **Errors:** one `AppError` tagged union; loaders skip bad lines and report a `skipped` count. No silent `try?`-style swallowing (ADR 0005).
- **Preferences are owned by Rust** (`Prefs`, ADR 0007). Never write app state under `~/.claude`.
- **Writes to Claude Code's files** go only through the safe-write primitive in `heimdall-core/src/config/write/` (ADR 0009).

## Icons

- Use Lucide icons **only through `src/components/AppIcon.vue`**. Never use emoji or custom icon assets for UI elements.
- Motion effects are named utilities (`bounce`, `pulse`, `breathe`, `variable-color`, `rotate`, `wiggle`, `replace`) from `src/styles/motion.css`, applied through `AppIcon`'s `effect` prop.
- **Every effect is gated by reduced motion** (`usePrefersReducedMotion`) and by the `showAnimations` preference.
- The mapping from Poirot's icon names to Lucide lives in `docs/design/icon-map.md`.

## Design tokens

- Colours, typography, spacing, radii and icon sizes are **CSS custom properties only**, defined in `src/styles/tokens.css` and exposed to Tailwind through `@theme` in `src/styles/main.css`.
- Never hard-code a colour or size in a component. Themes switch through `data-theme` on `<html>`; font scale is `--font-scale`.
- The token values come from Poirot's `Theme/PoirotTheme.swift` (tabulated in `docs/design/theme-tokens.md`).

## Security

The webview-to-IPC boundary is the only real control (ADR 0010). In short:

- `renderMarkdown()` is the only path into `v-html`, inside `src/lib/markdown/MarkdownView.vue`. ESLint's `vue/no-v-html` enforces this everywhere else.
- Links open only through the `open_external_url` command (http, https, mailto). The webview never navigates away from the app origin.
- The CSP has no `unsafe-eval`; the production CSP has no `unsafe-inline`.
- One capability file per window; no `fs` or `shell` plugin; no `opener:allow-open-path`.
- Code-execution writes (hooks, MCP servers) require a native confirmation from Rust.
- Processes launch with argument arrays only, never shell strings.
- MCP `env` and `headers` values are secrets: they never cross IPC and are never logged.
- Any change to commands, capabilities, the CSP or write paths needs security-auditor review.

## Parallel development (worktrees)

- Use one git worktree per active workstream branch, so Rust work in `crates/` and `src-tauri/` never collides with Vue work in `src/`.
- Worktree N runs with its own identifier so preferences never collide: `npm run tauri dev -- --config '{"identifier":"io.github.amine-bourouba.heimdall.dev<N>"}'`. The main checkout's development builds use `io.github.amine-bourouba.heimdall.dev`.
- Worktree N sets `HEIMDALL_DEV_PORT=1420+N` (for example 1421) for its Vite port.
- Debug builds read `HEIMDALL_CLAUDE_HOME` to point at a fixture tree; release builds ignore it.

## Feature development workflow

- Pick a task from `docs/tasks/` whose dependencies have landed. Read only that task and its Inputs.
- Deliver its Outputs, prove every acceptance criterion, get the named reviewers.
- Append one entry to `docs/progress-log.md`; never edit another entry.
- After editing any task file, run `python docs/tasks/check_backlog.py --poirot <path-to-poirot>`.

## New Feature Checklist

Every new feature or view must follow these steps:

1. Use existing patterns (list, gallery) for page content layout — do not invent new layout paradigms
2. Use markdown rendering as pertinent, through `MarkdownView.vue` (see Sessions and Plans for examples)
3. Add items to the universal search (Ctrl/Cmd+K): a provider in `heimdall-core/src/search/providers.rs`
4. Watch for file changes in the feature's folder or file for live updates: map its paths to an area in `heimdall-core/src/classify.rs` and subscribe the store to that area (ADR 0006)
5. Include in navigation history if pertinent (a Vue Router route)
6. Add Playwright visual baselines for new screens
7. Add new information to the `README.md` file
